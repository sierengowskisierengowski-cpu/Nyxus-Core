What Meli Is
Meli is a native Linux desktop application for managing, monitoring, and analyzing honeypot infrastructure. It is a complete threat intelligence command center built for security researchers, home lab operators, and infrastructure defenders. Meli aggregates data from multiple honeypot services, classifies threats automatically, enriches attacker data with external intelligence APIs, generates reports, and alerts the operator in real time when significant events occur.
Meli is not a toy. Every feature is functional. Every clickable element leads somewhere real. Every visualization shows real data. There are no placeholders, no "coming soon" sections, no mock data after development is complete.
Tech Stack
Frontend: Native GTK4 with PyGObject (Python bindings)
Backend: Python 3.12
Database: SQLite for local storage (default) with optional PostgreSQL backend for users with existing PostgreSQL infrastructure
Real-time messaging: Local MQTT broker (Mosquitto) for event ingestion and inter-component communication
Background workers: Python systemd user services
Packaging: PyInstaller for binary, with separate Arch PKGBUILD, .deb, and AppImage build targets

Authentication & Security
First Launch Setup Wizard
On first launch, Meli displays a multi-step wizard:

Welcome screen — name, version, author (Joseph Sierengowski), brief description
Master password creation — minimum 12 characters, complexity requirements, confirmation field, strength meter
Optional 2FA setup — TOTP via QR code OR YubiKey enrollment
Configure first honeypot — at least one data source required to proceed (can be skipped with warning if user plans to add later)
API key entry (optional) — fields for AbuseIPDB, GreyNoise, VirusTotal, Shodan, IPInfo. Each can be skipped and added later in Settings
GeoIP database download — downloads MaxMind GeoLite2 City and ASN databases (requires free MaxMind account API key OR offers bundled fallback)
Setup complete — summary screen, "Launch Meli" button

Login / Lock Screen

Shown on every app launch
Master password required
2FA prompt if enabled (TOTP code or YubiKey touch)
"Forgot password" displays recovery instructions (recovery requires GPG-signed recovery file generated during setup)
3 failed attempts: 60-second lockout, then 3 more attempts: 5-minute lockout, then 3 more: app closes and writes security event to log
Shake animation on incorrect password
Lock screen also appears after configurable idle timeout (default 10 minutes)
Keyboard shortcut Ctrl+L locks immediately from anywhere in the app
Lock screen has subtle indication of last login time and source

Encrypted Storage

Severity Classification System
Every event is classified into one of five severity levels by the classification engine.
Severity Levels

INFO — Port scans, single failed login attempts, generic probes, banner grabbing
LOW — Repeated probes (>5 from same IP), single-honeypot brute force, known scanner IPs
MEDIUM — Sustained brute force (>20 attempts), credential stuffing across multiple usernames, known dictionary patterns, multi-honeypot probes from same source
HIGH — Successful authentication, command execution attempts, file download attempts, suspicious commands (wget, curl, base64 decode, chmod +x)
CRITICAL — Malware payload captured, known APT IoC match, RCE execution confirmed, post-exploitation behavior (privilege escalation attempts, persistence mechanisms, lateral movement), data exfiltration patterns, Tor exit node + critical activity

Classification Engine

Rule-based with default ruleset shipped in default_rules.yaml
Users can add/edit/disable rules via Settings → Classification Rules
Each rule has: name, description, severity, conditions (event field matchers), priority
Rules evaluated in priority order; highest matching severity wins
IoC matching against known threat feeds (loaded daily): abuse.ch, AlienVault OTX, Emerging Threats
Behavioral patterns: rate analysis, sequence detection, multi-event correlation

HTTP Ingest API (Alternative to MQTT)
Meli runs a local HTTP server on configurable port (default 17654) that accepts honeypot events via POST.
Endpoint
POST http://localhost:17654/api/v1/events/ingest
Headers

Authorization: Bearer <honeypot_token>
Content-Type: application/json

Body
Same as MQTT event schema above.
Responses

202 Accepted on successful ingestion
401 Unauthorized for invalid token
400 Bad Request for malformed event
429 Too Many Requests for rate limiting (configurable per source)

Health Check Endpoint
GET http://localhost:17654/api/v1/health — returns 200 + JSON status

Stops and disables systemd services
Removes binaries and application files

Non-Negotiables

No dead-end clicks. Every clickable element either performs an action, opens a view, opens a dialog, or links to documentation. No buttons that do nothing.
No "coming soon" sections. Either a feature ships in v1.0 or it's not in the UI. Future features go in CHANGELOG roadmap section, not visible in app.
No mock data after development. All views show real data or empty-state messaging that explains what data will appear when there is some.
No silent failures. Every error logged. User-facing errors shown via toast notifications with actionable messages.
No data loss without confirmation. All destructive actions require explicit confirmation.
No external network calls without user consent. Enrichment APIs only called for IPs in the database. No telemetry by default. No update checks unless enabled. Initial GeoIP download is the only first-launch network activity, and the wizard explains it.
No plaintext secrets on disk. API keys, session tokens, master password all encrypted.
